# 操作手册式视频与文档验收方案

状态：2026-09-10 用户已确认并授权本地实施；源码与本地样例已实现，专项及仓库隔离检查通过。安装或发布不在本次授权内。

## 目标与范围

验收增加可选的交付形式。选中后，同时交付真实操作视频和可独立阅读的操作手册，让用户看清每一步如何操作、为何需要该步骤，以及如何确认结果。

当前缺口：已有流程与证据要求，但缺少手册式视频、逐步说明和视频文档对应要求；当前源码未发现通用录屏实现。不能用规则修改或文件存在来证明已经具备完整交付能力。

## 推荐选择

在已有任务或合同的 Verification Plan / Real Validation Plan 中记录“验收交付形式”，只提供两种选择：

| 选择 | 行为 |
| --- | --- |
| 标准验收（默认） | 保留现有报告与证据要求 |
| 操作手册式验收：视频 + 文档 | 在完成相同功能验收的基础上，必须交付两种可阅读、可对应的材料 |

用户明确要求视频和文档时直接选用第二项，不重复询问。选择属于当前任务；不增加全局设置、产品界面或新的命令行参数。选择不改变业务验收范围和操作权限。

## 用户收到什么

- `操作演示.mp4`：真实操作录制，带中文步骤标题和必要解释；多个业务流程可分为编号视频，避免一个超长视频。
- `操作手册.html`：可离线打开，截图内嵌，视频使用同目录相对链接；不依赖远程字体、脚本或图片。文档不播放视频也能照着操作。
- 视频和文档放在同一可交付目录。原始录制、日志与中间文件保留在既有证据目录，最终交付文件不能只留在即将删除的临时目录。大文件不默认进入 Git。

首版不强制配音或 PDF。中文说明必须出现在视频画面中，不能只放在旁边的文档。PDF 如后续被明确要求，再作为同源导出格式验证。

## 每一步的统一内容

复用当前验收场景中的步骤，补足“步骤编号、操作目标、入口/控件、具体动作、必要解释、预期结果、实际结果、视频时间段和截图”。这是一份共享步骤内容，不分别手写两套业务说明。

文档顺序：适用功能与版本/环境、角色和前置条件、场景目录、逐步操作、完成结果与确认方式、当前范围内必要的异常处理。凭据不写入材料。文档用日常操作语言，不把内部协议字段和调试日志塞入正文。

每一步在视频中展示操作前状态、实际动作及操作后反馈；文档用相同步骤编号给出操作说明、关键截图和对应时间码。需要解释的内容包括输入要求、为什么等待、如何判断成功，以及当前业务范围已有的注意事项。

## 录制与可读性标准

- 从正常用户入口开始，完整覆盖当前批准的业务流程和最终结果；不得用 API 绕过要求通过 UI 完成的动作。
- 视频来自同一候选版本、实例和关联业务对象的真实操作。模拟器或模拟数据只能支持已批准的模拟边界，材料明确标识。
- 以 1080p 为推荐起点；实际验收按最终播放尺寸能看清控件、输入和反馈判断，必要时调整界面缩放或局部放大。
- 关键点击、输入、确认及结果展示保持正常速度；动作目标清楚，字幕有足够阅读时间且不遮挡关键内容。等待可剪短或加速，但必须标明，不能剪掉失败或关键状态转换来制造成功。
- 中文步骤标题与解释覆盖所有必要操作；鼠标高亮不是强制技术，但操作位置必须辨认得出。配音可选，静音观看也能理解。
- 截图截取或采集自同一次实际流程；时间码指向最终导出的视频。编辑后重新检查时间码，不能沿用原始录屏时间。
- 输入、页面和录屏避免暴露密码、令牌及无关个人信息；遮挡不能掩盖本次判断所需的结果。

## 最小实现边界

1. 原位扩展共享业务验收规则 `plugins/atlas-workflow/skills/team/references/business-acceptance.md`：定义选择、双件交付和质量要求。Task / Team 继续引用这一处，不复制完整规则。
2. 在当前规划交接的最小入口提示记录该选择；实现时检查 `skills/clarify` 的现有合同编写入口，避免在每个技能重复维护选项。`project-verification` 仍是可选索引，不能作为启用前提。
3. 使用 `workflow/templates/business-playback.md` 的既有逐步结构扩充可选手册字段，或在共享参考中给轻量样例。未选中时不要求额外文件，不强制创建 BAF。
4. 在一个可信本地样例的项目 adapter 中完成真实录制、步骤信息采集与 HTML 输出。优先复用该项目已有浏览器/录制和媒体工具；能力或依赖不足时报告具体缺口，不自动安装。首版不建设跨浏览器、桌面、CLI、设备通用录屏平台。
5. 对采用 `codex-web-acceptance` 的项目，复用现有 `adapter.argv` 传项目自身支持的选项；启用时将视频、文档声明为 `required_evidence`，用一个独立材料 validator 检查同一交付 claim。validator 使用已有 `input_context: "run-context@1"` 读取实际产物，不只检查文件引用。通用配置拒绝额外字段，不能直接塞入自造的 `delivery_mode`。步骤依据来自冻结合同或登记的内容证据；argv 指向的外部文件内容不会因此自动冻结。
6. 文档中的步骤与时间码是共用内容来源；机器可核对步骤覆盖、媒体有效性和引用一致性，但不能单凭存在或 hash 判断“像手册、能看清”。最终仍需实际播放和阅读复核。

当前配置和证据机制已有冻结配置/合同、必需文件、内容 hash、独立 validator 与 audit，无需新建 schema、证据数据库或验收状态机。没有接入录制的项目不能因为选择了此模式就宣称自动支持；只能记录为交付能力待补齐。

## 失败与结果表达

功能结果和材料结果分别报告。例如：“业务流程检查通过；操作视频缺失，手册式交付未完成。”选中后缺视频、缺文档、遗漏必要步骤、无法辨认操作、时间码错位或来源不一致均不能报告交付完成，也不能静默退回标准验收。

现有 web runner 在必需材料/validator 失败时会使对应 attempt 失败，整体 `technical_status` 按既有多次运行聚合规则保留 `failed` 或 `unstable`，均不得报告选中模式交付完成。解释失败来自交付材料，不能据此编造业务动作失败，也不能覆盖原有真实失败。未选中时继续遵循现有证据采集规则。

生成视频不额外授权业务写入、现场动作或重跑。若素材不足，需要重录有副作用的操作，先检查现有权限和数据条件；没有权限时保留已取得的结果并说明交付缺口。
