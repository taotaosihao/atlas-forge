## 一、已确认方向

1. 减少 Clarify 的无关说明、需求漂移和过度设计，保留当前任务必需的工程判断与安全保护。
2. 较大且存在实质工程取舍的任务，Clarify 自动启动多角色讨论，简短说明原因和分工，不再逐次征求同意。
3. 角色按实际工程问题选择。“长期演进＋当前交付”适合多数场景，是常用组合，不是固定阵容。业务、开发、测试的职能分工不能替代工程方案之间的比较。
4. 各角色在合同成稿前提出自己的方案，相互回应并修订；主 agent 负责取舍，最终只保留一份实施合同。

## 二、Clarify 的日常行为

### 先读已有上下文，只补实际缺口

先确认用户要得到什么、已经决定什么、还缺什么会改变结果的信息。保持用户目标与权限稳定，同时允许工程方案在证据和讨论中变化；不能把主笔的第一种实现想法提前冻结成需求。

- 不再因为请求只有一句话，就机械输出九项说明。已有上下文足够时直接收敛；清楚的小任务不额外创建讨论流程。
- 只问会改变行为、范围、数据、安全、权限或验收的问题；能从现有代码、材料和批准记录查明的事实，先自行查明。
- 输出围绕本次目标、明确不做的边界、必要取舍、最小实现与可达验收组织，不强求固定篇幅或空栏目。
- 使用业务和日常中文；编排、合同版本、身份摘要等工程细节留在必要的内部材料，不塞进用户界面或常规回复。

### 按实质取舍启用协作

自动共同制定适用于较大任务中的关键方案选择，例如跨模块相互影响、复杂业务状态、数据或权限边界，以及不同方案会显著改变实施与维护成本。主 agent 用一句话说明为何需要哪些视角。

文件多、改动量大、请求短、标注 non-tiny 都不是充分条件。大批重复工作可以并行查证和划分责任，但不强制安排多立场辩论。用户明确要求协作时按其要求执行，不以默认判断取消用户选择。

复用现有原生协作能力，不要求先启动完整 Team 执行流程。角色人数按有用的独立视角确定，遵守现有宿主容量与分波限制；波次上限不是角色总数、讨论轮数或完成条件。不改调度运行时、模型策略或宿主配置。

### 选择角色，不建设角色体系

关键取舍适合长期与当前投入比较时，直接沿用常用组合；不适合就替换、合并或补充。例如迁移任务可以侧重兼容迁移与结构简化，不必保留原组合后继续加人。

| 常用视角示例 | 需要提出的内容 |
| --- | --- |
| 长期演进 | 自洽的技术方向、维护成本、难以逆转的选择；哪些边界现在值得建立，哪些假设尚无依据。 |
| 当前交付 | 基于现有代码的最小完整实现、复用路径、已知局限与以后调整的条件；必要质量、安全和验收不可省略。 |
| 主 agent | 相同的用户原意和事实入口、争议归纳、证据判断，以及最终合同。 |

各角色都可提出替代方案和改变立场。不能把长期角色等同于增加设计，也不能让当前交付角色只负责删减。Ponytail 的减法原则不赋予任何一方默认否决权：当前已有的重复维护、错误来源或高代价返工，可以支持现在做适度结构调整。

### 讨论和收敛

1. 共享用户原话、已批准决定、相关代码与限制，不只分发主笔重述，也不要求先有完整合同才能讨论合同。
2. 各视角独立提出工程方案、依据与关键假设；共识不必伪装成分歧。
3. 针对会改变实现、风险或验收的争议相互回应，必要时补查调用链、现有实现或可安全执行的反例检查。
4. 各方修订方案，主 agent 按证据和目标取舍。不能以投票代替判断、机械折中，或把全部意见并成新增需求。
5. 相关角色对照用户原意、已批准决定和讨论结果回看最终条款。正文只保留本次实施、明确不做的边界和必要理由，讨论历史不混入执行正文。

需求含义稳定、实现与依赖有落点、验收前提合法可达、影响交付的分歧已处理后即可收敛。不以固定轮数、时长或全票同意作为完成条件。无关改进不延长本次讨论；没有新证据且仍缺关键事实时，明确缺口，不反复交换相同意见。

只有需要改变用户目标、权限、必要验收或作出用户专属取舍时才回来询问。协作者不可用时遵守现有安全降级规则，说明缺失视角；不能把单 agent 结果称为已完成的独立多角色讨论，必要视角缺失且无法安全判断时停止该项结论。

## 三、同步解决已有规则的直接冲突

### 复用设计决定，不重新发明需求

先复用本任务已有、仍有效的设计和批准，只确认新增或改变的含义。没有指定文件不等于没有业务决定；也不能反过来把已有文字、沉默、测试通过或 agent 共识当成批准。

需要机器交接的路径继续使用现有 A/C/D/E 结构、同任务身份与有效批准校验。若只缺结构，整理范围必须严格限于已有明确批准覆盖的内容；任何新增语义仍需确认，不得伪造引用、沿用失效身份或把历史批准提升为当前授权。业务决定清楚但现行校验所需的有效绑定仍缺失时，只报告该具体缺口，不宣称交接已通过，也不默认重新展开整套业务设计。

这一改动必须核对 Clarify、Product Design 的直接路由、[method adapter](../../../plugins/atlas-workflow/skills/product-design/references/method-adapter.md)与[交接校验器](../../../plugins/atlas-workflow/contracts/product-design/validators/design-handoff.js)的承接关系，避免入口接受而下游拒绝。本次不引入新批准协议、不重做 Product Design，也不放宽正式发布批准或可操作原型的现有权限边界。

### 缩短默认正文，低频细则按需读取

[Clarify 主体](../../../plugins/atlas-workflow/skills/clarify/SKILL.md)保留判断路径、最小输出、读取触发条件和关键边界；详细合同编写、协作操作和正式发布细则放入插件内按需读取的相关参考材料，优先复用已有位置。保留清楚的触发与路径，不靠“另见文档”隐去必要规则。

不同内容由各自权威位置维护，避免复制同一套版本或准入教程。引用以加载的插件位置解析，不能依赖目标项目恰好是 Atlas Forge 仓库。须验证隔离安装布局中的可达性，不能只检查仓库链接。

### 对齐新合同模板和校验

现有新编写规则要求普通合同 semantics v5／执行计划 v3，正式发布合同 semantics v6／执行计划 v4；两个模板仍默认 v4 并指导普通 v3，测试还锁定旧指引。这是已有缺陷，不是新增合同能力。

修正[草稿模板](../../../workflow/templates/implementation-contract.md)、[最终模板](../../../workflow/templates/implementation-contract.final.md)及对应测试，消除重复版本教程，并用实际模板产物经过现有新编写校验。保留历史合同读取兼容，不升级 schema、不增加生成器、不迁移历史合同。

轻量澄清不必自动生成机器合同；一旦选用正式机器合同，就继续满足其现有必需字段与校验，不能用精简提示语规避要求。

### 保持所有直接入口一致

同步核对 [Codex manifest](../../../plugins/atlas-workflow/.codex-plugin/plugin.json) 的说明与默认提示、必要 README、相关命令入口和专项测试。只更新与本方案直接冲突的描述，不改写无关技能。

源码与专项验证完成后，文档索引的现行 Clarify 规则指向当前技能源码；这不代表已安装的 main-only 规则被刷新。普通 Task/CW 不因此自动升级为 Team，正式发布路径保持独立。

## 四、最小落地范围与顺序

以下范围已由“开始实施”授权；本轮不扩展至安装、发布或真实行为回放。

2. **相邻规则与模板一致性。** 处理已有批准复用的直接承接冲突、按需引用与模板版本偏差；保持身份、权限、历史兼容和发布保护。
3. **验证与交付。** 检查真实模板产物与隔离布局，整理有限回归样本及预期；另获明确授权后执行真实会话回放，未回放时标明行为改善尚未验证。按实际影响面执行仓库验证矩阵，并分别报告各层证据。

不新建角色目录、选角评分器、讨论协议或投票状态机、通用语义校验器、评测平台、合同生成器，也不因长期意见建立必须执行的后续路线图。原生协作、SDD 协议、版本发布工具及既有授权模型不在重构范围。

禁止顺带修改 Multica、共享 agent 配置、marketplace、已安装 cache 或 workflow runtime。源码变更不推导出本机或 gewu-office 同步、cachebuster 更新、发布或安装权限。

## 五、怎样验证优化有效

### 有限回归样本

从已有诊断会话中保留最小、去标识化输入和预期判断；不把原始日志、私人信息或大段历史复制进通用插件。

| 场景 | 需要观察的结果 |
| --- | --- |
| 请求很短，但已有上下文完整 | 不机械补九项说明，不重复询问已决定事项；该保留的权限与验收不丢失。 |
| 较大且存在相互影响的工程选择 | 自动启用不同工程视角，在合同成稿前确有方案提出、相互回应与必要修订。 |
| 大批重复改动，没有实质方案取舍 | 可并行查证，但不强制组织立场辩论。 |
| 工程关键取舍不同于长期／当前投入 | 能选择更适合的角色，不强制保留常用二人组。 |
| 已批准设计复用，以及批准缺失或含义改变 | 前者不重新设计和重复确认；后者不能伪造批准或沿用失效交接。 |
| 大屏数据与托盘校正 | 不自造逐点质量体系或通用异常中心；仍保护未知值真实性、旧命令执行及并发风险。 |
| UX 需求编号相同、含义却被改变 | 对照原意指出语义漂移，不能因编号存在或 lint 通过而接受。 |
| 合同要求无法合法构造的业务状态 | 修改不成立的验收假设或暴露真实缺口，不新增未授权生产写入口。 |
| 当前存在重复规则导致的错误 | 长期视角能提出有证据的有限结构改进，当前交付视角能接受必要投入并补充验证，不预设最小 diff 胜出。 |
| 必要协作者不可用 | 准确报告缺失与降级，不伪称多角色讨论完成。 |

### 分清验证层级

- 文档与规则检查：验证说明存在、入口一致；不证明真实 agent 行为改善。
- 模板产物和现有 lint：验证合同结构、版本、授权绑定与历史兼容；不证明自然语言忠实于用户目标。
- 隔离安装布局：验证插件内引用实际可读；不等于真实安装已更新。
- 真实会话回放：观察范围忠实、工程视角差异、相互回应和可达验收，才能评价行为改善；不以 agent 数、意见数、字数或一致投票打分。
