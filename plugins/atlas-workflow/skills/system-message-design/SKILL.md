# 系统提示语设计规范

让用户一眼知道发生了什么，必要时知道下一步怎么做。默认使用简短、自然、专业的中文。

## 先删，再写

- 先判断提示是否必要。标题、字段、按钮和状态已表达清楚的内容，不再重复说明。
- 筛选、切换、展开等日常操作不报成功；保存等显式操作保留一处清楚反馈。
- 界面只保留当前操作需要的信息，完整流程和低频概念放入就地帮助。
- 精简不以字数为目标，不能删掉影响判断的对象、限制和后果。

## 怎么写

- **结果在前，动作明确。** “已保存”“请选择负责人”“数量不能超过可用库存 12 件”。错误说具体问题，有可执行的下一步才补充。
- **自然、直接。** 去掉客套、卖萌、责备和重复解释，不用“温馨提示”“系统开小差啦”“请您务必”。
- **术语一致。** 同一对象保持同一名称；保存、提交、审核、发布、作废、删除不能混用。
- **准确到对象和范围。** 多对象操作写明名称或数量，校验对应当前字段，数值范围与单位和实际约束一致。
- **只说已知事实。** 不猜测失败原因，不虚构自动保存、恢复、重试能力；不把“联系管理员”当通用解决办法。
- **面向使用者。** 技术错误放入按需展开的详情。使用完整的可翻译句子，避免碎片拼接、变量泄露和格式噪音。

## 放在哪里

| 场景 | 默认方式与要点 |
| --- | --- |
| 字段错误 | 字段下方说明问题；跨字段错误关联到具体字段 |
| 普通成功 | 一处短反馈；页面已清楚表达结果时省略浮层 |
| 空状态 | 区分尚无记录和筛选无结果；有真实入口才提供新建或清除筛选 |
| 加载失败 | 留在失败区域，支持时提供重新加载；不要伪装为空数据 |
| 业务阻塞 | 说明具体对象和原因，有权限及入口时直达相关详情 |
| 异步或批量结果 | 持续可查看的进度和结果；失败明细可定位到对象 |
| 权限问题 | 区分无权限、功能未开通和登录失效，给对应处理方式 |
| 高影响操作 | 一次确认，说明对象及关键后果，按钮使用真实动作 |

需要处理的错误不能只靠短暂浮层、颜色或鼠标悬停表达，键盘和触屏用户也应能定位并处理。

## 反馈必须符合实际行为

- 请求受理、处理中、业务完成分别表达。“已提交”不等于“已完成”，进度到 100% 不代替最终结果。
- 部分成功、主操作成功但关联处理失败，应分别说明；结果未知时不要直接判定失败并诱导重复操作。
- 区分可继续的警告与硬性阻塞。提示类型与含义一致，并核对错误后是否真的停止了操作。
- 必填、拒绝空白、拒绝零是不同条件；`0`、`false` 不默认视为空。范围核对比较符、边界值及单位。
- 上传中、上传失败、未选择文件分别提示。失败后不承诺输入已保留、已清空或已回滚，除非实际如此。

## 确认框

普通保存和日常操作不默认加确认。需要确认时，标题写动作与对象，正文只补关键后果，按钮说明实际作用。

例如：标题“覆盖上次导入的数据？”；正文“本次导入将替换上次导入的数据。”；按钮“取消 / 覆盖导入”。只有确实无法恢复才补充这一后果。

不要用“提示”作通用标题，不重复“如已核对请点击确定”。已被业务规则禁止的动作直接说明原因，不展示可以继续的确认框。

## 使用与检查

先核对当前场景、术语、约束和实际结果；涉及交互时检查提示后的动作、状态与页面去向，不只替换词条。不要为了新文案改变业务规则或增加操作步骤。

单条请求直接给文案，多条用简短对照表。交付前确认：是否必要、是否准确、是否能处理、是否重复打扰；对动态名称、数量和多语言做相关核对。只解释影响选择的理由。
