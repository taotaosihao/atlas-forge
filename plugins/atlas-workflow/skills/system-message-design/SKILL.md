# 系统提示语设计规范

让用户一眼看懂发生了什么，并在需要处理时清楚下一步怎么做。默认使用简短、自然、专业的中文。如果项目已有 `DESIGN.md` 等设计规范，在其适用范围内以项目规范为准。

## 先减后写

- 先判断提示是否必要。标题、字段、按钮和界面状态已经表达清楚的信息，不再重复说明。
- 筛选、切换、展开等即时生效的操作，界面变化本身就是反馈，不必再提示“操作成功”；保存、提交等操作给出一处明确反馈即可。
- 界面上只放当前判断和操作需要的信息，完整流程说明或低频概念放进按需展开的帮助里。
- 精简不是单纯追求字数少，不能把影响判断的操作对象、限制条件和后果一并删掉。

## 怎么写

- **结论在前，下一步明确。** 直接写“已保存”“请选择负责人”“数量不能超过可用库存 12 件”。报错先说清具体问题；只有当用户确实有办法处理时，才补充下一步怎么做。
- **语气平实直接。** 不客套、不卖萌、不推诿，也不用居高临下的口吻；不用“温馨提示”“系统开小差啦”“请您务必”。
- **用词前后一致。** 同一业务对象在全系统保持同一名称；“保存”“提交”“审核”“发布”“作废”“删除”含义不同，不要混用。
- **用业务语言，不用内部黑话。** 不要把内部指标名或技术术语直接搬上界面，比如把“数据新鲜度”改写为“数据更新于 3 分钟前”。
- **按钮直接写要执行的动作。** 点下去实际发生什么，按钮就写什么。例如弹窗用来取消运输，主按钮就写“取消运输”，不写含义不符的“确认已到位”；此时关闭弹窗的按钮改用“返回”或“关闭”，避免同时出现两个“取消”。
- **写清具体对象和限制条件。** 多对象或批量操作要写明具体名称或数量；表单校验要针对当前字段，提示里的数值范围和单位必须与实际约束一致。
- **只写已确认的事实。** 不猜测失败原因；如果固定模板要求填写原因，只写已查明的原因，未查明时如实说明原因未知。不虚构自动保存、恢复或重试能力，也不拿“请联系管理员”当万能回复。
- **报错给用户看，技术细节收起来。** 堆栈、错误码等技术信息放入按需展开的详情。正文写通顺完整的句子以便翻译，避免拿零碎词组硬拼，更不要把变量名、空值或原始格式符号直接漏到界面上。

## 中文书写

项目已有的术语和写法优先，其次参考已上线的同类文案；都没有约定时，按以下默认做法处理。

- 标点使用全角（，。；：？！），并列项之间用顿号“、”。纯英文、编码、路径、小数、数值范围、比例，以及时间和 IP 地址中的冒号保留半角。
- 提及按钮、菜单或选项名称时加中文双引号，如点击“保存”；菜单路径写成“文件”>“导出”。
- 正文省略用“……”。若项目惯例在按钮或菜单后加省略号表示后续还有弹窗，用单字符“…”而非三个英文句点“...”；无此惯例则不加。
- 数字后带量词，如“3 台机床”“{count} 个托盘”；量词前用“两”不用“二”，如“两台机床”。
- 数量、编号、时间和规格用阿拉伯数字。KB、MB、Hz 等技术单位保留英文，时长、件数等日常单位用中文，如“5 分钟”。
- 多用主动句，少用生硬的“被”字句：写“同步数据后”，不写“数据被同步后”。
- 中文里的英文词不加复数，写“所有 PLC”。除 ID、PLC、CNC 等业务通用缩写外，非必要不用缩写。
- 中英文及数字之间是否留空格、日期时间用什么格式，均沿用项目现有写法并在全产品保持统一。日期、数字和金额通过统一的格式化方法输出，不手工拼接字符串。
- 操作提示要契合设备的交互方式：触屏终端不写“悬停查看”“右键”，同时面向鼠标和触屏的界面统一用“点击”等通用说法。
- 大多数提示直接陈述事实即可，不必加人称；确需称呼用户时，全产品统一用同一种称呼。
- 按钮用动词短语；开关或切换控件的两个状态标签词性要对称（如“启用 / 停用”）。

## 展示位置与方式

| 场景 | 默认方式与要点 |
| --- | --- |
| 字段校验错误 | 就近显示在对应字段下方；跨字段校验错误关联到相关字段 |
| 常规操作成功 | 给出一处简短反馈即可；页面状态变化已足够明显时不再弹浮层 |
| 空状态 | 区分“暂无数据”和“无匹配筛选结果”；页面确有对应功能时才提供“新建”或“清空筛选”入口 |
| 加载失败 | 在加载失败的区域就地提示，支持重试时提供“重新加载”；不要把加载失败显示成空数据 |
| 业务阻塞 | 点明受阻的具体对象和原因；用户有权限且存在对应页面时，提供直达入口 |
| 异步或批量结果 | 提供可随时查看的进度与汇总结果；失败明细能定位到具体对象 |
| 权限与登录问题 | 区分“无访问权限”“功能未开通”和“登录已失效”，分别给出对应的处理方式 |
| 高风险操作 | 弹一次确认框，写清操作对象与关键后果，按钮直接写具体动作 |

需要用户处理的错误，不能只靠短暂浮层、单纯变色或鼠标悬停来提示，要保证只用键盘或触屏也能定位并处理。

## 反馈必须符合实际行为

- **区分“已提交”“处理中”和“已完成”。** 请求刚发出不等于处理完成，进度条到 100% 也不能代替最终业务结果。
- **如实反映部分成功与结果未知。** 部分成功，或主操作成功但关联步骤失败时，要把成功和失败的部分分开说清；请求超时、结果未知时不要直接判定失败，避免误导用户重复提交。
- **区分可继续的警告与硬性拦截。** 提示样式要与严重程度一致；报硬性错误后，操作必须真正中止。
- **校验提示与实际判断逻辑一致。** “未填写”“不能全为空格”“不能为 0”是不同条件，不要把合法的 `0` 或 `false` 当成未填写；数值范围需核对比较符、边界值和单位。
- **文件与表单状态实事求是。** “上传中”“上传失败”“未选择文件”要分别提示；操作失败后，只有系统确实保留了输入、清空了表单或回滚了数据，才能在提示中这样说明。

## 确认框

普通保存和日常可逆操作不弹确认框。确需确认时，标题写明动作与对象，正文只补充关键影响，按钮写出点击后的实际作用。

例如：标题写“覆盖上次导入的数据？”，正文写“本次导入会直接替换上次导入的数据。”，按钮用“取消 / 覆盖导入”。只有确实无法恢复时，才补充“此操作不可恢复”。

不要拿“提示”当通用标题，也不要写“如已核对请点击确定”这类套话。已被业务规则禁止的操作应直接说明原因，不要弹出看似可以继续的确认框。

## 使用与检查

先核对当前场景、业务术语、校验规则和实际执行结果；涉及交互时一并检查提示出现后的按钮状态、后续动作与页面去向，不能只做字面替换。不要为了迁就文案而改动业务规则或增加操作步骤。

单条修改直接给文案，多条修改用简短对照表，只在涉及取舍时说明理由。交付前自查：是否真的需要、是否符合实际行为、用户能否据此处理、是否造成重复打扰，并核对动态名称、数量拼接和多语言场景是否自然。
